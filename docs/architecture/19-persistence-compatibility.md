# M1.3 persistence and snapshot compatibility

## Existing format and restore path

The runtime store directory is selected by `cmd/synora-core` from configured
state paths and remains unchanged. The active files are:

| File | Format / schema | Behavior |
| --- | --- | --- |
| `state.json` | JSON object, `schema_version: universal-store/v1` | Materialized revision, snapshots, bounded projections, dedupe and action state, and redacted resident metadata |
| `journal.jsonl` | One JSON `universal-store/v1` record per line | Append-only commit recovery source; each successful append is synced before the state file update |
| `segments/*.jsonl` | Same journal record format | Immutable audit history produced by compaction; names are ordered lexically during read |
| `erase.marker` | `universal-store/erase/v1` text marker | Crash-recovery marker; a remaining marker causes history removal before normal opening |

Snapshot schemas embedded in the records are `cognitive-snapshot/v1`,
`cognitive-snapshot/v2`, and `cognitive-snapshot/v3`. The active V1 Core
persists V1 snapshots; V3 candidate records preserve both the projected V1
snapshot and the optional V3 snapshot. Decisions and action requests retain
their existing schema fields and JSON names.

Open first reads and decodes `state.json`, rejects malformed JSON or an
unsupported store schema, validates resident state, replays WAL lines newer
than the materialized revision, then validates archived journal records and
memory bounds. Corrupt state, journal or archive returns an error; records are
not silently skipped except duplicate/already-materialized records during
replay. Erase writes and syncs the marker before deleting journal and archived
history, persists an empty state, removes the marker and syncs the directory.

M1.3.1 moved the Go definition of the identity-free
`ResidentGalleryRecord` into `internal/foundation/contracts`; the Store state
map and existing JSON field names, field types, optional-field semantics,
policy version and timestamp representation remain the same. The old
`internal/cognitivecore.ResidentGalleryRecord` name is a type alias. Decision,
snapshot, commit and journal record definitions remain in cognitivecore.

## Persistence extraction

The new `internal/foundation/persistence.ReplaceSynced` helper now performs
the existing temp-file write, file sync, close, rename and containing-directory
sync sequence for `state.json`. JSON encoding and schema validation remain in
the Universal Store because their concrete record types are still declared in
`internal/cognitivecore`. WAL append, compaction, replay, restore and erase
remain there as well. This is a partial persistence extraction; no database,
new path, migration, or on-disk schema was introduced.

## Compatibility evidence

Compatibility fixtures are generated by the existing implementation in
tests, not copied from production data. Existing tests cover:

- V2 and V3 snapshot golden feature vectors and preservation of the immutable
  V2 feature prefix.
- Restart, journal replay, duplicate-event handling, action-outbox claims,
  action-result folding and resident gallery persistence.
- Crash before/after WAL append, corrupt state and journal rejection,
  compaction/restart equivalence, corrupt archive rejection, and interrupted
  erase recovery.
- Canonical snapshot equality before and after compaction.

No historical production snapshot fixture was present in the workspace. The
existing tests compare exact canonical JSON around compaction and semantic
restart state; they do not claim byte compatibility against production files.
M1.3 must rerun these tests after its boundary changes. No production snapshot
was read, changed or migrated.

M1.3.1 adds exact synthetic JSON compatibility coverage for the extracted
resident contract and reruns the existing serialized Go suite, architecture
checker and format-specific checks. The pinned fixture is generated from the
pre-extraction tags, not production data. See
`24-persistence-contract-compatibility.md` and `25-m131-validation.md`.
