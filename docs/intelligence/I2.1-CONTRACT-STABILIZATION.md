No unresolved architectural ambiguity remains within the authorized I2.1 scope. The signed time-delta representation uses an overflow-checked integer seconds difference plus nanoseconds before conversion to finite float64 seconds. Typed `time.Time` input cannot express malformed timestamp text; malformed serialized timestamps are rejected by Go's standard JSON time parser before encoding.

## 3. Temporal encoding and causal separation

The encoder preserves `event_time`, `observed_at`, and `received_at` as separate declared times, including the original time-zone representation. It computes:

```tex
age_seconds = event_time - observed_a
```

- `observed_at < event_time` yields a positive age.
- `observed_at == event_time` yields zero.
- `observed_at > event_time` yields a negative age and is accepted.
- Receive delay does not change the age. `received_at` is carried separately and is not used as a plausibility reference.
- No clock tolerance, timestamp correction, clamping, stale threshold, or status inference exists.
- Out-of-order and replayed records are encoded independently; the encoder has no cross-batch clock or replay state.
- The Go typed contract uses `time.Time.IsZero()` to represent a missing timestamp. Consequently, the exact instant `0001-01-01T00:00:00Z` is indistinguishable from an omitted timestamp and is not accepted where a timestamp is required. This is a current technical contract boundary; no pointer-field/schema migration was made.

Translation does not prevent future-data leakage. A future runtime/training input assembler must enforce availability at prediction cutoff using actual receipt/availability provenance. It must exclude records unavailable at that cutoff even when their event/observation timestamp is earlier, and preserve original timestamps for records it includes. This assembler is documented as a future I3 requirement; it is not implemented here.

## 4. Status, identity, value, and graph fidelity

- All seven supplied statuses remain distinct: observed, unknown, unavailable, unsupported, stale, conflicting, and absent. Future age does not change status. Unknown is not false/zero; unavailable is not false/zero; absent remains distinct from unknown. Existing input-contract rules governing which statuses may carry values/timestamps remain enforced.
- Same-attribute records from different sources or at different times are retained. Exact duplicate observation records are rejected. Source-specific conflicting records are preserved; no source wins.
- Number, Boolean, and category retain their declared type. Numeric unit tokens and category strings remain symbolic. No unit conversion, category vocabulary, or embedding is added.
- Entity IDs and kinds remain explicit. Directed relation subject/object, kind, source, and validity interval are preserved. Cycles and isolated entities are permitted; no edge reversal, symmetrization, topology inference, or spatial interpretation occurs.
- Entity, observation, and relation permutations produce equivalent canonical output. Input immutability is verified by comparing the complete JSON serialization of the typed batch immediately before and after `Encode`.

## 5. Numeric representation and precision

The current 14-name contract is a structured intermediate, not a complete model tensor. Status and declared-type masks plus numeric values and signed age are numeric. Booleans remain Boolean; categories, entity/attribute/source references, units, provenance, and evidence remain symbolic; relations remain structured directed records. Numeric normalization, category vocabularies, entity-to-number mappings, graph projection, and temporal history/window representation are not implemented.

Input numbers must be finite and within float32 magnitude. A non-zero float64 that would underflow to float32 zero is rejected. Values above the largest finite float32 are rejected, so valid inputs cannot become infinity. Values representable in float32 can round because float32 has a 24-bit significand; that precision loss is inherent in the declared v1 field and is not silently described as exact. Tests cover negative, zero, maximum, minimum non-zero float32, underflow, overflow, NaN, infinity, and deterministic rounding.

## 6. Limits and allocation behavior

The experimental v1 package constants define fixed per-batch budgets: 512 entities, 2,048 observations, 2,048 relations, 192 bytes per qualified identifier, and 256 bytes per provenance/evidence reference. They are compile-time constants, not runtime configurable and not universal SynoraOEM limits.

Exactly-at-limit collection lengths are accepted; one over is rejected. Identifier and evidence string lengths are checked during validation. `Validate` checks top-level collection lengths before allocating its entity and duplicate-detection maps. `Encode` validates the complete input before allocating output slices and sorting copies. Accepted-input work and memory are bounded by the declared counts and field-length caps, though output and sorting copies are proportional to input size. Rejection is atomic: an invalid batch returns an empty `EncodedBatch`; there is no truncation or partial encoding.

## 8. Remaining deferred design work

These items are not unresolved choices for the I2.1 encoder correction, but must be decided by their owning milestone before use:

- I3 must define prediction-cutoff clock domain and availability evidence, and prove late-arriving records cannot leak into a past input.
- A later model-facing projection must version category vocabularies, numeric normalization, entity mapping, graph-to-tensor representation, and any temporal history/window.
- Foundation-to-Intelligence identity mapping, unit registry/conversion, confidence semantics, and upstream definitions for stale/absent remain deferred; I2.1 adds no adapter or policy.
- The zero-time sentinel limitation described above remains a technical v1 boundary unless a future contract version adopts optional timestamp fields.
