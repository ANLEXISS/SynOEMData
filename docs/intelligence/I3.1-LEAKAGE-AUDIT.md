**Status:** PARTIAL; formal audit incomplete because the task-contract stop gate was reached

## Scope and method

Inspected the dataset artifact types, generation/label construction, availability selection, and serialization code. No learned model, preprocessing fit, or baseline was run. This is a source-level traceability inventory, not a complete statistical exploitability audit.

## Findings

### Direct target leakage

The intended `WriteArtifacts` model-input envelope serializes only batch, encoded batch, and selected availability metadata; it does not directly serialize target labels or scenario/home/split index fields. Existing I3 tests check for literal scenario identifiers and `ground_truth`/`target` strings in the serialized model input. **No direct target field was observed in the intended serializer.** This does not prove resistance to arbitrary metadata injection or every field-level proxy; adversarial tests were not run in I3.1.

### Temporal leakage

The generator selects records with `ReceivedAt <= cutoff`, including records whose `ObservedAt` lies in the future, consistent with the I2.1 translation contract. The code path is visible and existing I3 tests exercise late observations and future-dated clock drift. The I3.1 adversarial cases for replay, changed cutoff, source clock, and post-cutoff metadata were NOT RUN. The observation cutoff implementation is therefore PARTIAL as a qualification result.

### Identifier and label-proxy risks

- Home, source, provenance, and emission IDs are stable SHA-derived strings. Whether their patterns or repeated reuse predict labels was **NOT EVALUATED**.
- Scenario names are absent from input files by intended design, but scenario fixtures alter observable event count, status, entity/attribute shape, values, timestamps, and relations. This is a **POTENTIAL GENERATOR SHORTCUT**, not automatically leakage: the evidence can be legitimate at the cutoff, but robustness across varied scenarios was not evaluated.
- Task D has scenario-specific positive rules (`routine-change` and `unexpected-presence`) and a daily-routine rule derived from `familyOrdinal`; the latter can correlate with stable home/family identity. This is a **POTENTIAL LABEL-PROXY RISK**. ID-only and scenario-only baselines were NOT RUN.
- Task C is `edge_added` exactly for the modified-topology fixture; the hidden scenario label is excluded, but task difficulty and proxy predictability are **NOT EVALUATED**.
- Task E labels conflicting-source examples inconsistent. Visible disagreement is an **INTENTIONAL VISIBLE SIGNAL** for a consistency diagnostic, not itself leakage. The task is only a narrow synthetic rule.
- A/B generic state targets lack a target entity/attribute reference. This is a **CONFIRMED TASK-CONTRACT DEFECT**, not a finding that input contains the target. It prevents a well-defined leakage/difficulty evaluation for these tasks.

### Split leakage

The implementation puts each home group and topology family in a single split and reserves five scenario templates from training. The current graph family set has six fixed motifs; repetitions within a family are isomorphic. Exact duplicate inputs, linked trajectories, identifier memorization, and whether all claimed topology groups are distinct across splits were **NOT EVALUATED** in this I3.1 run. The policy cannot establish generalization beyond these generator rules.
