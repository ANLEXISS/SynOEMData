# Cross-Module Scenario Catalog

These are proposed test cases. “Support” reflects code present now; no missing zone, physical command, or hardware capability is treated as implemented.

| Scenario | Required concepts | Current implementation support | Missing contracts / fakes | Expected interaction and feasibility |
|---|---|---|---|---|
| Unknown person enters a camera zone | Camera/zone, track, class, identity unknown, boundary event, confidence/evidence, incident policy | Unknown-person Vision events and incident identity kinds exist; `foundationv1.Zone` is only a nonproduction, non-geometric reference contract. No production zone transition model. | Production zone/frame/rule and enter event; fake camera + detector + track + zone geometry | Vision -> Integration event bridge -> Core decision/incident -> Foundation Store. **Partially feasible** only as unknown person sighting, not zone entry. |
| Known resident crosses a virtual boundary | Resident identity, line geometry/direction, camera/preset, track continuity | Resident identity and event sequence references exist. No line geometry or crossing contract. | Frame-bound polyline, direction, resident/track reference, evidence; fake track sequence | Vision -> Core, store event and evaluate existing identity behavior. **Not feasible as crossing behavior** until contract/runtime exists. |
| Vehicle present outside an activity zone | Vehicle class, zone occupancy, duration and activity-window condition | Python detects vehicle class; no generic zone/activity grammar. | Zone, activity schedule/time zone, occupancy observation; fake vehicle track/clock | Vision -> Integration -> future condition evaluator. **Not currently testable as semantics**; class detection alone testable. |
| Person loitering near an entrance | Entrance relation, zone, dwell threshold, tracking gap, evidence | Track/episode and temporal keys exist; no entrance zone/loiter rule. | Zone purpose, dwell start/end, threshold/window, continuity policy; fake clock + tracker | Vision -> Core decision/incident. **Not feasible as loitering** without rule contract; deterministic synthetic sequence can validate a future rule. |
| Camera loses tracking temporarily | Camera/track source, gap/continuity reset, unknown vs exit, event-time | Versioned segment gap, continuity reset, camera health and Python edge tracking exist. | Shared gap semantics and policy for incident/zone state | Vision worker -> Integration -> Core. **Partially feasible now** through segment/continuity contracts; verify no false exit claim. |
| Camera PTZ preset changes | Camera, PTZ coordinate frame, preset, view-specific rule association | Camera ID and online observation exist; no PTZ/preset contract found. | PTZ pose/frame, preset token, transition and validity time; fake PTZ adapter | Integration camera adapter -> Vision rule context. **Not currently feasible** beyond generic capability string. |
| Network device becomes unavailable | Device identity/capability, health state, last-seen, recovery | Camera and worker/network degraded/offline events, runtime health exist. | General device health/reason/freshness record; fake station source/network adapter | Platform network source -> Integration Discovery -> Bus/Core status. **Feasible for current network/camera path**, not all device classes. |
| Unauthorized door command | Principal/role, lock state, intent, policy, authorization result, command and execution result | Security API/Bus auth, resident roles, Core safety gate and abstract action exist. No typed door lock/access authorization result or physical executor. | Actor authorization reference and fail-closed decision; fake policy + lock adapter | API/Integration auth -> Core policy -> Automation -> result; **partially feasible** for API/abstract action rejection, not real lock state or physical actuation. |
| Automation dispatch failure | Rule/decision, action request/result, idempotency, outbox, retry | Core outbox and abstract Automation dry-run request/result exist; store failure coverage present. | Module-owned rule condition is absent; Adapter outcome must distinguish simulation from execution | Core -> Foundation outbox -> Automation -> Core result. **Feasible for dry-run and persistence failure**, adapter failure only as injected future seam unless interface exists. |
| StateStore crash and recovery | Snapshot/WAL/revision/dedup/outbox, recovery point | Foundation Store replay, compaction, persistence injection and tests exist. | Process-level crash checkpoint catalog and power-loss filesystem qualification | Core -> Foundation Store close/reopen. **Feasible in software** with temp dirs and injected persistence failures; not physical power-loss proof. |
| Concurrent or out-of-order observations | Source sequence/epoch, event vs ingest time, idempotency, order policy | Event carries timestamp, received-at, epoch, sequence; bus and Store concurrency tests exist. | Explicit ordering/gap/window/late-arrival contract shared by modules | Multiple fake producers -> Bus -> Core -> Store. **Partially feasible** for transport/store ordering; domain-level late observation behavior is inconsistent/not generalized. |
| Unsupported hardware capability | Capability descriptor, version, constraints, support state, command result | Device and camera expose string capability lists; runtime/model status has unavailable errors. | Typed capability descriptors and standardized `unsupported` outcome | Integration capability discovery -> Core/Automation policy; fake device advertises unsupported operation. **Partially feasible** for current string capability filters; no generalized schema. |

## Minimum fixture standard

Each future fixture should include IDs, logical time, expected interactions, versioned payloads, capability state, event-time/ingest-time distinction, evidence references, and an explicit expected unsupported/unknown outcome where applicable. Keep one fixture for a fully supported current path and one for each missing contract marked “not implemented”; never count the latter as a passing behavior test.
